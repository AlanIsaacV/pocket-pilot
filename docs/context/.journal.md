### 2026-04-16 — Sync pagination fix (initial sync data loss)

- **Bug:** On fresh device install, only the first 20 records per entity were persisted locally (accounts, categories, transactions truncated — others unaffected because they had <20 records). Root cause: all backend `List*` handlers default to `page_size=20` via `parsePage(req.Page)` when no `PageRequest` is provided. Each remote service made a single gRPC call, ignored `response.page.next_page_token`, and then committed `last_synced_at`. Delta syncs thereafter only fetched NEW changes, so the missing records were never reconciled.
- **Fix (frontend-only, no backend change):**
  1. All 9 remote services (`*_remote_service.dart`) now accept optional `pageToken: String?` and `pageSize: int = 100` (max the backend allows) and always attach a `PageRequest`.
  2. All 9 sync handlers (`*_sync_handler.dart`) wrap `_remote.list*()` in a `do/while` loop that accumulates `SyncItem`s and continues while `response.hasPage() && response.page.nextPageToken.isNotEmpty`. Final `syncedAt` comes from the last response.
  3. Existing silent `catch (_)` in `_pullEntity` is unchanged — if any page fails mid-loop, the whole pull aborts and `last_synced_at` is NOT advanced, so the next cycle retries from the original cursor (no partial persistence).
- **Why page_size=100:** Backend `parsePage` clamps to `[1, 100]`. Larger pages minimize round-trips on first sync (50M-row edge cases are not in scope).
- **Docs updated:** `architecture/sync_protocol.md` — corrected the pagination section (previously stated delta syncs were NOT paginated; in reality both delta and full sync are paginated and the client must loop).
- **Files modified:** 9× `*_remote_service.dart`, 9× `*_sync_handler.dart`.
