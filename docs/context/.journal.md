### 2026-05-09 — Fase 9 notification_capture: refactor UX (sección "Por confirmar" + picker jerárquico)

**Problema:** tres puntos de fricción en el feature.

### 2026-04-26 — Fase 8 notification_capture: package selection dinámica + loop comunitario

**Alcance:** reemplaza la allowlist hardcoded de 2 strings (BBVA) en `BankNotificationListenerService.kt` por una decisión per-device del usuario, alimentada por (1) un log liviano sin PII de packages observados, (2) una pantalla "Mis bancos" donde el usuario marca cuáles capturar, (3) sync per-user de aliases entre devices, y (4) un loop comunitario anónimo que sugiere nuevos bancos al backend. El admin promueve sugerencias a un catálogo global pull-only que beneficia a todos los usuarios sin redeploy.

**Restricción técnica firme:** Google Play rechaza `QUERY_ALL_PACKAGES` para apps de finanzas. El picker se alimenta exclusivamente de packages que el NLS ya vio notificar; la observación es device-side y no requiere permiso adicional al de NLS.

**Decisiones (cerradas en brainstorming):**
- **Discovery del picker = log persistente sin PII.** El NLS Kotlin escribe `(package_name, posted_at)` a una tabla nueva `package_observations` para TODA noti que llega — sin title/text/big_text. Captura transients que el usuario ya descartó del shade. Trade-off vs. snapshot vía `activeNotifications`: el log da UX accionable (histórico real) a costo de una escritura por noti del SO. Coverage > footprint para esta feature.
- **Modelo de aliases = híbrido `bank_id?` + `display_label`.** Si el package está en el catálogo global, el cliente prefilla `bank_id` (desbloquea pickup automático del parser y match con `account_card_mappings`). Si no, `bank_id=NULL` y el alias queda libre (display-only). Descartado: solo texto libre (perdía link automático con parser); solo dropdown del catálogo cerrado (bloqueaba el caso "agregar banco no catalogado aún", justo lo que Fase 8 resuelve).
- **Migración existing users = mig FE 016 popula `watched_packages` con BBVA.** Cero fricción tras update; la captura sigue funcionando exactamente igual. Descartado: forzar re-onboarding (hubiera cortado captura durante el gap). `bank_aliases` NO se seedea en mig 016 — el catálogo global ya tiene BBVA en `bank_packages`, así que la resolución `_bankIdForPackage` sigue funcionando aunque el usuario nunca pase por el picker.
- **UX flow = settings opcional + post-onboarding nudge.** `OnboardingPermissionScreen` sigue como Step 1 (permiso); cuando el lifecycle observer detecta el flip false→true al volver de Ajustes, redirige a `/settings/notification-capture/banks?firstTime=1`. Después siempre accesible desde Settings → Captura de notificaciones → "Mis bancos". Descartado: onboarding obligatorio inline (bloquea al user si el log está vacío en device nuevo); solo settings sin nudge (riesgo de conversión catastrófica).
- **Sync entities = nuevas constantes.** `EntityBankPackage` (global pull-only, syncOrder=4 igual que `notification_parser`) y `EntityBankAlias` (user-scoped sync, syncOrder=5 igual que cardmapping/txrule). No reusar entities existentes — cursores propios para que un cambio en una no invalide las otras.
- **Promotion bump admin = `bumpAllUsers`** igual que `notification_parsers`. Volumen bajo (admin-driven), <10k usuarios sigue siendo aceptable.
- **`package_suggestions` gating = `help_improve_app=ON`** (toggle existente del settings, default ON, opt-out). Coherente con `candidate_parsers`. La sugerencia contiene solo `package_name` + `proposed_label` + `proposed_bank_id?` — sin texto crudo. Sin user_id por diseño (anonimato).

**Decisiones puntuales:**
- **NLS cache invalidation rebind-only.** El NLS lee `watched_packages` en `onListenerConnected()` y cachea en memoria como `Volatile Set<String>`. Cuando el usuario marca un package nuevo en Dart, no aplica hasta el próximo rebind. Pragmatismo: rebind ocurre en cada boot/permission toggle/OS event, raro que el usuario quede esperando. Si el lag se vuelve molesto, agregamos `refreshWatchedPackages` al MethodChannel `com.pocketpilot/notification_capture` (TODO documentado en el código).
- **`package_observations` con PRIMARY KEY natural** (package_name) en SQLite y UPSERT con `MAX(last_seen_at, excluded.last_seen_at)`. Idempotencia natural; el sweeper de retención solo necesita marcar `purged_at` (no borra rows — el package_name no es PII).
- **Backfill de `package_observations` desde `captured_notifications`** en mig 016 (`INSERT INTO ... SELECT ... GROUP BY package_name`). Devices con historial pre-Fase-8 abren el picker con datos útiles desde el primer momento. Sin esto, BBVA quedaría sin entry en el log hasta la próxima noti.
- **Reuso del retention sweeper de Fase 6** extendido con un `List<PurgeRunner>` en lugar de un único runner. La compat con tests/legacy se mantiene vía `forTesting` (single runner) y un parámetro opcional `observations:` en el factory de producción. `package_observations.last_seen_at < cutoff` se marca con `purged_at` (no se borra el row — la columna `package_name` es metadata útil, no PII).
- **Orden de los sync handlers en `main.dart`.** `bankPackageSyncHandler` se registra entre `parserSyncHandler` y `accountCardMappingSyncHandler` para mantener la coherencia visual del orden (todos los pull-only globales antes de los user-scoped). `bankAliasSyncHandler` se registra después de `transactionRuleSyncHandler` por la misma razón.
- **`Repository._bankIdForPackage` ahora es async.** Antes era un switch sincrónico; ahora consulta `bank_aliases.getByPackageName` primero y `bank_packages.getByPackageName` después. Llamada solo en el path LLM fallback (no en el match local, que ya tiene `parser.bankId`), así que el costo extra de 1-2 lookups por noti no-matcheable es aceptable. Fallback `'unknown'` si nada matchea — el `_resolveAccount` falla en silencio y la UI obliga al user a elegir cuenta.

### 2026-04-26 — Fase 4 LLM fallback: ParseNotification RPC + candidate_parsers + toggles

**Contexto del bug:** Tras bumpear el parser BBVA MX a v2 server-side, las 8 notificaciones del usuario seguían en `status='unparseable'` localmente. `processInbox` solo procesa `status='received'`, así que los nuevos patterns no las tocaban.

**Lección:** No se puede confiar en `adb exec-in` para reemplazar la DB en un device con NLS activo. Para futuros debugging del flujo de captura, exportar la DB es seguro pero modificarla y pushar de vuelta no.

### 2026-04-16 — Sync pagination fix (initial sync data loss)

- **Bug:** On fresh device install, only the first 20 records per entity were persisted locally (accounts, categories, transactions truncated — others unaffected because they had <20 records). Root cause: all backend `List*` handlers default to `page_size=20` via `parsePage(req.Page)` when no `PageRequest` is provided. Each remote service made a single gRPC call, ignored `response.page.next_page_token`, and then committed `last_synced_at`. Delta syncs thereafter only fetched NEW changes, so the missing records were never reconciled.
- **Fix (frontend-only, no backend change):**
  1. All 9 remote services (`*_remote_service.dart`) now accept optional `pageToken: String?` and `pageSize: int = 100` (max the backend allows) and always attach a `PageRequest`.
  2. All 9 sync handlers (`*_sync_handler.dart`) wrap `_remote.list*()` in a `do/while` loop that accumulates `SyncItem`s and continues while `response.hasPage() && response.page.nextPageToken.isNotEmpty`. Final `syncedAt` comes from the last response.
  3. Existing silent `catch (_)` in `_pullEntity` is unchanged — if any page fails mid-loop, the whole pull aborts and `last_synced_at` is NOT advanced, so the next cycle retries from the original cursor (no partial persistence).
- **Why page_size=100:** Backend `parsePage` clamps to `[1, 100]`. Larger pages minimize round-trips on first sync (50M-row edge cases are not in scope).
- **Docs updated:** `architecture/sync_protocol.md` — corrected the pagination section (previously stated delta syncs were NOT paginated; in reality both delta and full sync are paginated and the client must loop).
- **Files modified:** 9× `*_remote_service.dart`, 9× `*_sync_handler.dart`.
